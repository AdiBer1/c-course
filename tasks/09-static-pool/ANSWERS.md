# Task 09 — Understanding questions

## Q1. Where in memory does your pool's storage live (stack, static, heap)? When is that memory reserved, and what does that mean for the linker's RAM report?

Answer:
The Pool is a static array; therefore, it resides in static memory—not on the stack or the heap. This memory is allocated during the build process: the compiler and linker assign a fixed address in RAM to the array, and it persists for the entire duration of the program's execution. Consequently, the full size of the Pool is already accounted for in the linker's RAM report. If the chip lacks sufficient RAM, the build process will fail immediately, preventing the device from encountering memory shortages later during field operation. In this way, the worst-case scenario is identified before the program even begins to run.

## Q2. Why must a pool block be aligned to `_Alignof(max_align_t)`? What could happen on an ARM Cortex-M0 if someone stored a `uint32_t` at an odd address?

Answer:
The memory block must be capable of holding data of any type. Since each type has its own alignment requirement, we must determine a common alignment—essentially a multiple that satisfies the requirements of all types. The value `_Alignof(max_align_t)` represents the strictest alignment requirement among all basic types; ensuring alignment based on this value guarantees that any object stored within the block will be correctly aligned. The Cortex-M0 processor does not support unaligned memory access at all: any 32-bit read or write operation must occur at an address that is a multiple of 4. If an attempt is made to store a `uint32_t` at an odd-numbered address, the processor will trigger a `HardFault` exception, causing the device to crash or reboot. (In the C language, misaligned memory access is considered "undefined behavior," and tools like UBSan can detect such instances in a PC environment.)

## Q3. With `malloc`, a long-running device can fail to allocate even though enough bytes are free in total. Explain why, and why a pool of equal-size blocks cannot have this problem.

Answer:
When using `malloc`, memory blocks of various sizes are allocated and deallocated at different times. Over an extended period, the available memory becomes fragmented: it is broken up into many small "holes" situated between blocks that are still in use. An allocation request requires a single, contiguous span of memory; therefore, even if 1,000 bytes remain free in total, a request to allocate 200 bytes might fail if the largest "hole" in the memory is only 100 bytes. When using a pool, this issue cannot occur, because all blocks within it are of identical size, and each request allocates exactly one block—meaning any free block is suitable for any request. Consequently, if the value returned by `pool_free_count()` is greater than zero, the `pool_alloc()` operation will always succeed. (The drawback is that a request for less than 32 bytes results in the waste of the remainder of the block, and it is impossible to allocate a memory segment larger than a single block.)

## Q4. How does your `pool_free` detect a double free and a pointer that is not the start of a block? Why is it better to detect these than to silently accept them?

Answer:
The `pool_free` function compares the pointer against the starting address of each block using the `==` operator. If the pointer does not match the beginning of any block, it implies that it points either outside the pool or to the middle of an existing block; in such a case, the function returns `false`. If the pointer matches block `i`, but the value at `in_use[i]` is already `false`, it means the block has been previously released—a "double free"—and here, too, the function returns `false` without making any modifications. Detecting these scenarios is far preferable to allowing them to pass unnoticed. If a double free were permitted, the same block might subsequently be allocated to two different users, who would then overwrite each other's data; in such a scenario, the data corruption would only be discovered much later, far removed from the original point of failure. By rejecting the call, this mysterious bug is immediately transformed into an explicit error at the exact moment it occurs; this allows the caller to check the return value and report the issue.
